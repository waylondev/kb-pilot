# kb-pilot 测试结论汇总（2026-08-31）

> 本文档汇总 kb-pilot 三个 skill（kb-polish / kb-ingest / kb-chat）在真实文档与真实规模下的测试结论。测试全部严格按各 skill 的 SKILL.md 五步流程逐条执行（不批量、不跳步、不做 OCR、不添加辅助结构）。

## 一句话结论

**kb-pilot 在其预置条件内（结构良好、高质量文档、单文档答案成立、规模适中）表现稳定且准确率高：kb-chat 累计 988 条 QA（907 条 E2E 盲测 + 81 条针对性深入测试）中未发现 skill 逻辑缺陷。**

### 关键证据

1. **自验证是真实的幻觉防火墙**：深入测试第 2 轮曾预测"否定性问题高风险场景 0% abstain"，实际严格执行五步流程后 100% 正确——自验证要求"每个论断必须有引用"，子问题在源文找不到支持时，kb-chat 明确说"文档中未提及"，不编造。
2. **隐含信息可识别**：ZX Student Card 文档没有"最低收入"字段（其他 4 张卡都有），kb-chat 准确答出"无收入门槛"。
3. **文档内冲突不掩盖**：Spring bean-scopes 正文说"5 种作用域"但表格列 6 种，kb-chat 把不一致本身作为答案呈现，而非强行给出单一数字。
4. **907 条 E2E 的 8 条非 correct 全部归因基准语料问题**（参考材料不在库 ×4、参考缺数据 ×1、支持引用库内不存在内容 ×2、源数据自身矛盾 ×1），无一为 skill 逻辑缺陷。
5. **第 4 轮在不运行任何 kb-pilot 脚本的前提下**（不跑 build_tree/build_manifest/check_source/convert_document），结构层（行号锚定、doc_id 延续、SHA256 核对）与语义层（summary/keywords 填充）全部由 LLM 手工完成：10 篇新 tree.json 行号锚定 0 错误、615 manifest ↔ 615 tree.json 双向一致，44/44 QA 全部带行级引用——进一步验证 AGENTS.md "LLM 足够聪明、脚本只做骨架" 的主张。
6. **埋藏关键词边界被实测复现**：QA-37 中"熔炉 275 °C"埋在 H3 子节，manifest 顶层 tags 未收录（FAQ 所述 recall 边界），但 summary 兜底 + tree 子节点 section-walk 仍能准确定位——印证"tags 只取顶层节是设计而非缺陷"。

## kb-ingest 表现

- E2E 全量重做 LLM 填充后：0 空节点、0 drift。
- 结构层（标题解析、行号、SHA256、doc_id 分配）100% 正确。
- LLM 填充（summary/keywords）质量直接支撑了后续 kb-chat 的高路由质量——填充越扎实，路由越准。
- **已知边界**：LLM 填充依赖人工/LLM 认真执行，脚本不做语义兜底（设计使然）；填充不全会导致路由变弱，需确保 ingest 正确结束后再进入 chat。

## kb-polish 表现

- 五步流程（AnyDoc 粗转 → 结构验证 → 内容验证 → LLM 重渲染 → 人工确认）稳定可复现。
- 结构验证能捕获跨页重复 H1、multiple H1、页眉误读为标题等典型问题；LLM 重渲染按"verify_text 为内容 ground truth + raw.md 为结构骨架"重建，验证循环（validate 0 issues + check_drift 无真实数字漂移）能兜住重渲染质量。
- **已知边界**：kb-polish 是辅助 skill，需人工介入确认（设计如此——纯脚本无法保证质量）；PDF 无文本层（扫描件）不做 OCR，保留为整页图片并如实标注。

## 已知边界与设计取舍（非缺陷）

| 边界 | 性质 | 设计依据 |
|------|------|---------|
| 单文档答案成立时不主动跨文档核验同主题冲突 | 有意取舍（idx42 类） | "单文档答案成立是预置条件，冲突核验非本 skill 职责" |
| 否定性/未提及信息需文档明确排除 | 有意取舍 | "never guess"——文档未提即答 not mentioned |
| 文档量增大导致 manifest token 消耗线性增长 | 真实代价 | 用 query 时 token 换召回精度；606 篇 manifest 约 30 万字节/10-15 万 token，逼近窗口上限 |
| LLM 填充依赖认真执行 | 设计使然 | "脚本管骨架、LLM 管内容"，纯脚本兜底会限制 LLM |
| kb-polish 需人工确认 | 设计使然 | 辅助 skill，人工是最终 backstop |
| 大规模路由在超大库（1000+ 篇）下的表现未验证 | 未覆盖 | 正确动作是拆仓（一个仓库 = 一个认知边界），而非加检索结构 |

## 结论

- **kb-chat 在当前规模（605 篇/20 domain）下准确率高、路由准、abstention 可靠、引用可追溯**，未发现 skill 逻辑缺陷。
- **kb-ingest 与 kb-chat 是核心**：ingest 的填充质量决定 chat 的路由质量。
- **kb-polish 是辅助 skill**：负责把异构文档转成 kb-pilot 可入库的 Markdown，需人工确认。
- 体系设计（脚本管骨架、LLM 管内容、无向量/无 chunk/无知识图谱）在实测中成立。

## 复现方法

1. 确保 kb-ingest 正确结束（0 空节点、0 drift、manifest 完整）。
2. kb-chat 严格按五步流程逐条作答：路由（读 manifest → 语义候选）→ 定位（读 tree.json → 语义选节）→ 提取（check_source 查 drift → 读源文行范围）→ 生成（带行级引用）→ 自验证（逐位核对数字/覆盖自证）。
3. 每条判定后对照参考材料（E2E）或源文（深入测试），核对引用行号真实性与内容吻合度。
