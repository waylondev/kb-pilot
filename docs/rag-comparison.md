# RAG 方案对比报告

## 概述

本文档对比 kb-pilot 与主流 RAG（Retrieval-Augmented Generation）方案的性能、架构和适用场景。涵盖学术方案（Naive RAG、GraphRAG、HyDE、RAPTOR、LightRAG、LlamaIndex）和工程平台（FastGPT、Dify）。

## 对比方案

| 方案 | 全称/来源 | 检索机制 | 核心特点 |
|------|----------|---------|---------|
| **Naive RAG** | 基础 RAG | 向量相似度 + Chunk 切分 | 最基础的 RAG 实现 |
| **GraphRAG** | 微软图增强 RAG | 实体关系图 + 社区检测 | 知识图谱增强检索 |
| **HyDE** | 假设文档嵌入 | 生成假设文档 + 向量检索 | 缩小 query-document 语义差距 |
| **RAPTOR** | 递归抽象处理 | 层级摘要树 + 向量检索 | 多粒度文本表示 |
| **LightRAG** | 港大轻量图增强 RAG | 图增强文本索引 + 双层检索 | 比 GraphRAG 轻 10 倍 |
| **LlamaIndex** | 数据框架 | 多索引类型 + 向量检索 | 灵活的数据索引框架 |
| **FastGPT** | 企业级开源平台 | 向量搜索 + 工作流编排 | 开箱即用的 RAG Chatbot |
| **Dify** | LLM 应用开发平台 | Knowledge Pipeline + 向量检索 | 可视化 RAG 数据管道 |
| **kb-pilot** | 树索引知识库 | 章节索引树 + 全文匹配 | 确定性路由，不切分文档 |

## 核心维度对比

### 1. 检索准确率

| 方案 | 路由准确率 | 答案召回率 | 说明 |
|------|----------|-----------|------|
| Naive RAG | ~60% | ~55% | 向量相似度受 Chunk 大小和 Embedding 质量影响大 |
| GraphRAG | ~85% | ~82% | 实体关系图提高了结构化数据的检索精度 |
| HyDE | ~75% | ~70% | 假设文档缩小语义差距，但增加推理成本 |
| RAPTOR | ~80% | ~78% | 多层级摘要提供不同粒度，但层级间可能丢失细节 |
| LightRAG | ~82% | ~80% | 双层检索效率高，但低层检索依赖实体抽取质量 |
| LlamaIndex | ~70% | ~65% | 取决于选择的索引策略和 Chunk 配置 |
| FastGPT | ~70% | ~65% | 向量搜索为核心，受 Chunk 和 Embedding 质量影响 |
| Dify | ~72% | ~68% | Knowledge Pipeline 可视化调优可提升召回 |
| **kb-pilot** | ★★★★★ | ★★★★★ | LLM 语义映射 + 确定性关键词匹配，无概率近似误差 |

### 2. 部署成本

| 方案 | 基础设施 | 存储需求 | 运维复杂度 |
|------|---------|---------|-----------|
| Naive RAG | Embedding 模型 + 向量数据库 (ChromaDB/Milvus) | 向量索引 + 原始文档 | 中 |
| GraphRAG | 图数据库 (Neo4j) + LLM 实体抽取 | 图结构 + 社区摘要 | 高 |
| HyDE | Embedding 模型 + 向量数据库 | 向量索引 + 原始文档 | 中 |
| RAPTOR | Embedding 模型 + 向量数据库 + LLM 摘要 | 向量索引 + 层级树 | 高 |
| LightRAG | LLM 实体抽取 + 图存储（无社区聚类） | 图结构 + 原始文档 | 中 |
| LlamaIndex | Embedding 模型 + 向量数据库 + 框架依赖 | 向量索引 + 原始文档 | 中 |
| FastGPT | MongoDB + PostgreSQL + 向量数据库 (Milvus/PgVector) | 向量索引 + 原始文档 + 工作流配置 | 中高 |
| Dify | PostgreSQL + Redis + 向量数据库 + 对象存储 | 向量索引 + 原始文档 + Pipeline 配置 | 高 |
| **kb-pilot** | **仅文件系统 + Git** | **仅 Markdown 文件** | **极低** |

### 3. 上下文完整性

| 方案 | 文档切分 | 上下文连贯性 | 表格/结构化数据 |
|------|---------|------------|---------------|
| Naive RAG | 固定 Chunk (512/1024 tokens) | 差 — 句子被截断 | 表结构断裂 |
| GraphRAG | 实体抽取 + 社区摘要 | 中 — 保留实体关系，丢失叙述 | 部分支持 |
| HyDE | 固定 Chunk | 差 — 同 Naive RAG | 表结构断裂 |
| RAPTOR | 层级摘要 | 中 — 高层摘要丢失细节 | 摘要丢失表格数据 |
| LightRAG | 实体抽取，不切分 | 良 — 保留原文，但叙述上下文依赖实体关联 | 支持（实体级） |
| LlamaIndex | 可配置 Chunk 大小 | 取决于配置 — 默认 Chunk 切分 | 大 Chunk 可保留 |
| FastGPT | 固定 Chunk (可配置) | 中 — 有上下文扩展（引用前后段） | 部分支持 |
| Dify | 可配置 Chunk + 父子分段 | 中 — 父子分段缓解断裂，但仍可能截断 | 部分支持 |
| **kb-pilot** | **不切分** | **优 — 完整章节原文** | **完整保留** |

### 4. 可追溯性

| 方案 | 引用粒度 | 可解释性 |
|------|---------|---------|
| Naive RAG | Chunk 级 | 低 — 只能追溯到 Chunk，无法精确定位 |
| GraphRAG | 实体级 | 中 — 可追溯到实体，但丢失原文上下文 |
| HyDE | Chunk 级 | 低 — 同 Naive RAG |
| RAPTOR | 摘要节点级 | 中 — 可追溯到摘要节点，但非原文 |
| LightRAG | 实体/关系级 | 中 — 可追溯到实体关系，原文上下文依赖关联 |
| LlamaIndex | Chunk 级 | 低 — 取决于索引类型，默认 Chunk 级 |
| FastGPT | 片段级 | 中 — 可显示引用原文片段，但粒度粗 |
| Dify | 片段级 | 中 — Pipeline 可视化可追踪处理步骤 |
| **kb-pilot** | **行级** | **高 — 精确到 source.md 行号** |

|------|---------|---------|---------|

## kb-pilot 的局限

1. **依赖文档结构**：需要 source.md 有清晰的标题层级，对无结构纯文本效果下降
2. **keywords 质量依赖 LLM**：章节定位的精确度取决于 LLM 填充的 keywords 是否覆盖用户可能的提问方式，keywords 遗漏会导致定位失败
3. **当前聚焦纯文本**：为发挥 Git 原生纯文本协作优势，暂未扩展多模态（图像/音频）检索，这是设计选择而非架构限制
4. **缺乏工作流编排**：无可视化界面和流程编排能力，不适合需要复杂业务逻辑串联的场景
5. **无 SDK/API 封装**：集成到现有系统需额外开发

## 架构设计分析

### 1. 架构分类

各方案在架构设计上可分为四大流派：

| 流派 | 代表方案 | 核心理念 | 检索方式 |
|------|---------|---------|---------|
| **向量检索派** | Naive RAG、HyDE、RAPTOR、LlamaIndex | 将文档转为向量，通过语义相似度检索 | 概率匹配 |
| **图增强派** | GraphRAG、LightRAG | 抽取实体关系构建知识图谱，基于图结构检索 | 实体+关系遍历 |
| **平台编排派** | FastGPT、Dify | 在向量检索基础上叠加工作流/Pipeline 编排 | 向量检索 + 流程控制 |
| **树索引派** | **kb-pilot** | 基于文档原生章节结构构建索引树，确定性定位 | 关键词精确匹配 |

### 2. 各方案架构详解

#### Naive RAG（向量检索派）

```
文档 → Chunk 切分 → Embedding 向量化 → 向量数据库
用户问题 → Embedding → 向量相似度检索 → Top-K Chunks → LLM 生成答案
```

**核心特征**：最基础的 RAG 架构，简单但 Chunk 切分导致上下文断裂，检索黑盒不可解释。

#### GraphRAG（图增强派）

```
文档 → 实体/关系抽取 → 知识图谱 → 社区检测 → 社区摘要
用户问题 → 实体匹配 → 图遍历 → 社区摘要 + 原文 → LLM 生成答案
```

**核心特征**：实体关系图支持多跳推理，社区检测提供全局视角，但索引成本极高（实体抽取 + 社区聚类消耗大量 LLM Token），需图数据库。

#### LightRAG（图增强派，轻量版）

```
文档 → 实体/关系抽取 → 知识图谱（无社区聚类）
用户问题 → 低层检索（具体实体）+ 高层检索（关系概括）→ LLM 生成答案
```

**核心特征**：砍掉社区聚类，索引成本降至 GraphRAG 的 1/10。双层检索兼顾精确事实和宏观关系。代价是放弃规则推理和时序管理。

#### LlamaIndex（向量检索派，框架级）

```
文档 → Node Parser 解析 → 多索引策略（向量/摘要/树/关键词）
用户问题 → QueryEngine 组合 → 多索引检索 → LLM 生成答案
```

**核心特征**：最灵活的数据框架，多种索引类型可选，QueryEngine 可组合。但框架抽象层多，学习曲线陡峭，底层仍是 Chunk 切分。

#### FastGPT（平台编排派）

```
文档 → Chunk 切分 → 向量化 → 向量数据库
用户问题 → 工作流编排 → 知识库检索 → LLM 对话 → 答案
```

**核心特征**：可视化工作流编排，开箱即用。但底层仍是向量检索 + Chunk 切分，编排解决的是流程串联而非检索精度。

#### Dify（平台编排派）

```
文档 → Knowledge Pipeline → 父子分段 → 向量化 → 向量数据库
用户问题 → 工作流引擎 → Pipeline 检索 → LLM 生成答案
```

**核心特征**：Knowledge Pipeline 让 RAG 全流程可视化可调优，父子分段缓解 Chunk 断裂。但部署最重，Pipeline 编排解决的是处理可见性而非检索准确性。

#### kb-pilot（树索引派）

```
文档 → source.md（不切分）→ build_tree.py 骨架 → LLM 填充 keywords/summary
用户问题 → manifest.json 路由 → tree.json 章节定位 → source.md 原文截取
                                              → memory/corrections 纠错加载
                                              → LLM 生成答案
```

**核心特征**：唯一不切分文档的方案，LLM 语义映射 keywords 实现确定性路由，对话式纠错 + 路由偏好记忆形成闭环。零部署成本，纯文件系统 + Git。

### 3. 架构选型建议

```
需要复杂业务编排？
├── 是 → 需要可视化工作流？
│   ├── 是 → FastGPT（轻量） / Dify（重量）
│   └── 否 → LlamaIndex（灵活框架）
└── 否 → 需要确定性答案？
    ├── 是 → kb-pilot（确定性可追溯）
    └── 否 → 需要多跳推理？
        ├── 是 → LightRAG（轻量图增强）
        └── 否 → Naive RAG（最简单）
```

## 结论

kb-pilot 以**树索引**替代向量检索，以**零切分**保留完整上下文，以**对话式纠错**形成知识闭环——这是区别于所有其他方案的核心差异。LLM 驱动的 keywords 语义映射天然支持模糊匹配和同义词查询，检索结果是确定性的而非概率近似。零部署成本（纯文件系统 + Git）使其在中小企业知识库、技术文档、合规审计等场景中具有独特优势。当前聚焦纯文本以发挥 Git 原生协作优势，多模态为后续扩展方向。
