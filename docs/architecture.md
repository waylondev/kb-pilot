# 系统架构

## 设计哲学

kb-pilot 的设计基于一个核心假设：**LLM 足够聪明**。

类比人类学习知识的方式：拿到一本书，先看目录了解结构，定位到相关章节，阅读原文，回答问题。人类不需要向量检索、不需要把书切碎成 Chunk、不需要实体关系图——需要的是**目录**和**原文**。

kb-pilot 做的就是这件事：
- `tree.json` = 书的目录（章节标题 + 关键字索引）
- `source.md` = 书的原文
- `manifest.json` = 图书馆的书目卡片
- LLM = 阅读者

| 角色 | 做什么 | 不做什么 |
|------|--------|----------|
| 脚本 (build_tree.py) | 解析 Markdown 标题，生成目录骨架 | 不碰语义 |
| 脚本 (build_manifest.py) | 扫描 docs/ 目录，汇总书目卡片 | 不碰语义 |
| LLM | 读目录，读原文，理解问题，匹配章节，生成答案 | 不做的事由设计决定 |

### 为什么 LLM 不需要"拐杖"

传统 RAG 给 LLM 加了很多辅助结构——向量嵌入、Chunk 切分、实体关系图、多级路由层级——本质上是默认 LLM 不够聪明，需要这些"拐杖"来弥补。

kb-pilot 反其道而行：**把 LLM 当作会阅读的人，给它目录和原文，信任它自己理解**。

- 不需要别名表 → LLM 自己知道"贷记卡"和"信用卡"是同一个东西
- 不需要 infobox 摘要 → LLM 自己能从原文中提取关键信息
- 不需要倒排索引 → LLM 自己能从 keywords 中做语义匹配
- 不需要多级路由 → LLM 能从 manifest.json 的 tags 中直接定位文档

**给 LLM 的信息越少、越精准，它的表现越好。** tree.json 是一个精准的目录，不是一份冗余的元数据堆。

## 设计边界

### 我们做什么

1. **为文档建目录**：build_tree.py 解析 Markdown 标题生成 tree.json 骨架，LLM 为每个章节填充 summary 和 keywords
2. **为知识库建书目**：build_manifest.py 扫描 docs/ 目录生成 manifest.json，汇总所有文档的 tags
3. **让 LLM 阅读和回答**：kb-chat 的 6 步流程本质上是 LLM 在"找书 → 翻目录 → 读章节 → 回答问题"

### 我们不做（设计选择，不是能力缺陷）

| 不做的事 | 原因 |
|----------|------|
| 文档格式转换（PDF/Word → Markdown） | 转换质量不可控，交给客户自行处理 |
| 向量嵌入和向量检索 | LLM 的语义匹配比向量相似度更精准 |
| Chunk 切分 | 切分破坏上下文完整性，与"完整阅读"理念冲突 |
| 实体关系图 | LLM 不需要图结构来理解实体间关系 |
| 多级路由层级 | manifest.json 的 tags 足够 LLM 做文档定位 |
| 别名 / 重定向表 | LLM 自己理解同义词 |
| Infobox / 结构化摘要 | tree.json 的 summary 就是 LLM 自己写的摘要，不需要额外层 |
| 倒排索引 / TF-IDF | LLM 的语义匹配比字符串匹配更智能 |
| SDK / API 封装 | 纯文件系统，不引入服务化复杂度 |
| 多模态（图像/音频） | 聚焦文本，发挥 Git 原生协作优势 |

## 核心组件

### 1. 全局路由表（manifest.json）

`docs/` 目录下所有文档的索引，由 `build_manifest.py` 自动生成。

每个条目包含：
- `doc_id`：文档唯一标识
- `title`：文档标题
- `domain`：所属领域
- `summary`：文档摘要（从 tree.json 拼接）
- `tags`：关键词集合（从 tree.json 所有节点收集）
- `path`：文档相对路径

### 2. 章节索引树（tree.json）

单篇文档的目录结构，由 `build_tree.py` 生成骨架，LLM 填充语义信息。

每个节点包含：
- `id`：节点唯一标识
- `level`：标题层级（2=##, 3=###）
- `title`：章节标题
- `anchor`：Markdown 锚点（用于精确定位）
- `summary`：章节摘要（≤20 字，LLM 生成）
- `keywords`：关键词列表（3-8 个，LLM 生成）
- `start_line` / `end_line`：原文行号范围
- `children`：子节点列表

### 3. 原始文档

Markdown 格式的完整文档，不切分，保留所有原始内容和结构。文件名不限，约定为 `source.md`。

### 4. 元数据（metadata.yaml）

文档的元信息，包括 doc_id、标题、领域、维护人、转换质量等。

### 5. 记忆系统（memory/）

记忆系统让知识库具备"学习"能力，支持答案纠错和路由偏好记忆。

#### 5.1 纠错记录（corrections/）

当知识库原文存在过时或错误信息时，用户可以通过对话纠正，系统将纠正内容持久化。

**存储格式**：`memory/corrections/{doc_id}.jsonl`，每行一条 JSON 记录：

```jsonl
{"timestamp":"2026-08-01T10:00:00+08:00","question":"DeepSeek V3 参数量","correct_answer":"671B (MoE)，激活37B","doc_id":"doc_001","source_ref":"用户纠正","status":"active"}
```

**纠错状态**：

| 状态 | 含义 | 处理方式 |
|------|------|---------|
| `active` | 生效中的纠错 | 优先使用纠错后的答案 |
| `conflicted` | 存在冲突的纠错 | 展示所有版本，让用户选择 |

**纠错流程**：

```
用户指出错误
    │
    ▼
检查 memory/corrections/{doc_id}.jsonl
    │
    ├── 无相似记录 → 追加 active，用新答案回答
    ├── 有记录且答案相同 → 跳过（已存在）
    └── 有记录且答案不同 → 追加 conflicted，展示所有版本
```

#### 5.2 路由偏好（route_preferences.json）

记录用户明确表达的领域偏好，后续问答自动优先检索指定领域。

**触发方式**：用户说"我以后主要问股票"、"我主要关注技术领域"等。

**重要约束**：仅存储用户**明确表达**的偏好，不从对话历史中推断。

## 数据流

### 文档入库流程

```
原始 Markdown 文档
    │
    ▼
source.md（完整保留）
    │
    ├──► metadata.yaml（LLM 创建元数据）
    │
    ├──► build_tree.py ──► tree.json 骨架
    │         │
    │         ▼
    │    LLM 填充 summary + keywords
    │
    └──► build_manifest.py ──► manifest.json
```

### 问答流程

```
用户问题
    │
    ▼
1. 领域路由 ──► route_preferences.json + LLM 语义判断
    │
    ▼
2. 文档路由 ──► manifest.json（LLM 语义匹配 title + tags）
    │
    ▼
3. 章节定位 ──► tree.json（LLM 语义匹配 keywords）
    │
    ▼
4. 内容截取 ──► source.md（start_line → end_line）
    │
    ▼
5. 纠错加载 ──► memory/corrections/
    │
    ▼
6. 生成答案 ──► 答案 + 依据 + 置信度
```

## 取舍

任何系统设计都有取舍。以下是 kb-pilot 明确的选择：

| 我们选择 | 我们放弃 | 原因 |
|----------|----------|------|
| 确定性路由 | 模糊检索的高召回率 | 精准比全面更重要，找不到就明确说找不到 |
| 完整原文 | 高效存储 | 上下文完整性优先于存储效率 |
| LLM 全权理解 | 辅助结构带来的"保险" | 信任 LLM 能理解，不给它加拐杖 |
| 文件系统 + Git | 服务化/SDK | 简洁优先于集成便利 |
| 纯文本 | 多模态 | 发挥 Git 原生文本协作优势 |
| 客户自行转换文档 | 内置格式转换 | 不引入转换质量风险 |
| 目录级索引 | 段落级索引 | 目录比全文索引更接近人类阅读方式 |
