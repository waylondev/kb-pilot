# RAG 方案设计哲学对比

## 概述

本文档对比 kb-pilot 与主流 RAG 方案的**设计哲学**，而非性能跑分。跑分受测试集、LLM 模型、配置参数等多因素影响，不具备可比性。真正有意义的对比是：**面对同一个问题，各方案选择了什么解法，放弃了什么**。

## 四大流派

| 流派 | 代表方案 | 核心理念 | 对 LLM 的态度 |
|------|---------|---------|-------------|
| **向量检索派** | Naive RAG、HyDE、RAPTOR、LlamaIndex | 将文档转为向量，通过语义相似度检索 | LLM 需要向量辅助才能找到相关内容 |
| **图增强派** | GraphRAG、LightRAG | 抽取实体关系构建知识图谱，基于图结构检索 | LLM 需要实体关系图才能理解知识关联 |
| **平台编排派** | FastGPT、Dify | 在向量检索基础上叠加工作流/Pipeline 编排 | LLM 需要工作流编排才能完成复杂任务 |
| **树索引派** | **kb-pilot** | 基于文档原生章节结构构建索引树，LLM 自主理解和路由 | LLM 足够聪明，只需要目录和原文 |

## 各方案架构详解

### Naive RAG（向量检索派）

```
文档 → Chunk 切分 → Embedding 向量化 → 向量数据库
用户问题 → Embedding → 向量相似度检索 → Top-K Chunks → LLM 生成答案
```

**设计选择**：用向量相似度替代人工检索，简单但 Chunk 切分导致上下文断裂，检索黑盒不可解释。

### GraphRAG（图增强派）

```
文档 → 实体/关系抽取 → 知识图谱 → 社区检测 → 社区摘要
用户问题 → 实体匹配 → 图遍历 → 社区摘要 + 原文 → LLM 生成答案
```

**设计选择**：用实体关系图支持多跳推理，但索引成本极高（实体抽取 + 社区聚类消耗大量 LLM Token），需图数据库。

### LightRAG（图增强派，轻量版）

```
文档 → 实体/关系抽取 → 知识图谱（无社区聚类）
用户问题 → 低层检索（具体实体）+ 高层检索（关系概括）→ LLM 生成答案
```

**设计选择**：砍掉社区聚类，索引成本降至 GraphRAG 的 1/10。双层检索兼顾精确事实和宏观关系。

### LlamaIndex（向量检索派，框架级）

```
文档 → Node Parser 解析 → 多索引策略（向量/摘要/树/关键词）
用户问题 → QueryEngine 组合 → 多索引检索 → LLM 生成答案
```

**设计选择**：最灵活的数据框架，多种索引类型可选，QueryEngine 可组合。但框架抽象层多，底层仍是 Chunk 切分。

### FastGPT（平台编排派）

```
文档 → Chunk 切分 → 向量化 → 向量数据库
用户问题 → 工作流编排 → 知识库检索 → LLM 对话 → 答案
```

**设计选择**：可视化工作流编排，开箱即用。编排解决的是流程串联而非检索精度。

### Dify（平台编排派）

```
文档 → Knowledge Pipeline → 父子分段 → 向量化 → 向量数据库
用户问题 → 工作流引擎 → Pipeline 检索 → LLM 生成答案
```

**设计选择**：Knowledge Pipeline 让 RAG 全流程可视化可调优，父子分段缓解 Chunk 断裂。但部署最重。

### kb-pilot（树索引派）

```
文档 → source.md（不切分）→ build_tree.py 骨架 → LLM 填充 keywords/summary
用户问题 → LLM 语义路由 manifest.json → LLM 章节定位 tree.json → source.md 原文
                                              → memory/corrections 纠错加载
                                              → LLM 生成答案
```

**设计选择**：信任 LLM 的理解能力，只给它目录和原文。不做向量嵌入、不做 Chunk 切分、不做实体抽取、不做多级路由。越简洁，LLM 表现越好。

## 核心维度对比

### 1. 对 LLM 的信任程度

| 方案 | 设计假设 | 给 LLM 的信息 | 额外辅助结构 |
|------|---------|-------------|------------|
| Naive RAG | LLM 需要向量辅助 | Chunk 片段 | 向量数据库 + Embedding |
| GraphRAG | LLM 需要实体关系图 | 实体 + 社区摘要 | 图数据库 + 实体抽取 |
| LightRAG | LLM 需要实体关系图（轻量） | 实体 + 关系 | 图存储 + 实体抽取 |
| LlamaIndex | LLM 需要灵活索引 | 多种索引片段 | 框架 + 向量数据库 |
| FastGPT | LLM 需要工作流编排 | 检索片段 + 流程 | 工作流引擎 + 向量数据库 |
| Dify | LLM 需要 Pipeline 编排 | Pipeline 片段 | Pipeline 引擎 + 向量数据库 |
| **kb-pilot** | **LLM 只需要目录和原文** | **完整章节原文** | **无** |

### 2. 上下文完整性

| 方案 | 文档切分 | 上下文连贯性 |
|------|---------|------------|
| Naive RAG / HyDE | 固定 Chunk | 差 — 句子被截断 |
| FastGPT / Dify | 可配置 Chunk | 中 — 缓解但不根治 |
| GraphRAG / LightRAG | 实体抽取 | 中 — 保留实体关系，丢失叙述 |
| RAPTOR | 层级摘要 | 中 — 高层摘要丢失细节 |
| **kb-pilot** | **不切分** | **优 — 完整章节原文** |

### 3. 可追溯性

| 方案 | 引用粒度 | 可解释性 |
|------|---------|---------|
| Naive RAG / LlamaIndex | Chunk 级 | 低 |
| GraphRAG | 实体级 | 中 |
| **kb-pilot** | **行级** | **高 — 精确到 source.md 行号** |

### 4. 部署成本

| 方案 | 基础设施 |
|------|---------|
| Naive RAG / HyDE / LlamaIndex | Embedding 模型 + 向量数据库 |
| GraphRAG | 图数据库 + LLM 实体抽取 |
| FastGPT | MongoDB + PostgreSQL + 向量数据库 |
| Dify | PostgreSQL + Redis + 向量数据库 + 对象存储 |
| **kb-pilot** | **仅文件系统 + Git** |

### 5. 纠错能力

| 方案 | 纠错能力 |
|------|---------|
| 所有 RAG 方案 | 不支持 — 答案错误只能重跑全流程 |
| **kb-pilot** | **对话式纠错，持久化记忆，active/conflicted 状态管理** |

## 架构选型建议

```
需要复杂业务编排？
├── 是 → FastGPT（轻量） / Dify（重量）
└── 否 → 需要实体关系多跳推理？
    ├── 是 → LightRAG（轻量图增强）
    └── 否 → 需要确定性答案 + 零部署？
        ├── 是 → kb-pilot
        └── 否 → Naive RAG 或 LlamaIndex
```

## 结论

kb-pilot 不是一个"比 RAG 更好"的方案——它做了一个**不同的设计选择**：信任 LLM 的理解能力，只给它目录和原文，不添加任何辅助检索结构。

这个选择带来了零部署成本、确定性路由、完整上下文和行级可追溯的独特优势，但也意味着：
- 它不适用于需要模糊检索高召回的场景
- 它不适用于需要多模态检索的场景
- 它要求文档有清晰的 Markdown 标题结构
- 它的表现完全取决于 LLM 的能力

这不是缺陷，而是取舍。每个系统都在做取舍，重要的是取舍是否服务于设计目标。
